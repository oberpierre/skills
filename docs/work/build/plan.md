# build

**Branch:** `feature/build`
**Issue:** #30

The skill that builds a plan's slices serially, each in a fresh subagent, test-first and one commit per behaviour, challenged before it stops for review (ADR 0004).

## Inputs from other features

Requirements the `slice` feature placed on `build`, to be grilled with it:

- It reads the branch from the plan's `**Branch:**` line. It continues on that branch, creates it from the default branch and switches to it when on the default branch, and stops and asks on any other branch. Slicing changes no code, so the branch is created where the first change happens and no empty branch is left behind.
- It reads the default branch from `origin/HEAD` rather than assuming `main`, and asks when `origin/HEAD` is not set, as a remote added by hand leaves it.
- It sets a slice's row to `done` in the slice's own last commit, never in a commit of its own. A slice's range is then found from the plan's history: its head is the last commit that set its row to `done`, and its base is the head of the slice built before it, or the branch's merge-base for the first. While building, it keeps the commit a slice starts from in its own context and challenges `<start>..HEAD`.
- It carries out a `rework` slice from its note (squash, revert or rebuild) in place, behind a green gate, so the slice's commits stay together, then challenges the slice and stops for review.
- With `tracker: github`, it closes a slice's issue, by the plan's `Issue` column, when the slice is done, and closes as "not planned", with a comment naming the slice that absorbed it, the issue of a slice a rework removes.
- It closes the plan only once the user has approved the last slice (ADR 0007), and writes `Closes #<parent>`, from the plan's `**Issue:**` line, into the pull request body. It closes the parent issue itself only when there is no pull request, once the branch has merged.

## Decision log

- This feature ships `build` and its commit-style presets only. `setup`, `tdd`, `diagnosing-bugs` and `pr` stay separate features. Until `tdd` exists, the coding agent's instructions carry their own short test-first rule. On a red gate classed as a defect in its own code, `build` offers to debug in the session. Each later skill then replaces one line of `build`.
- `build` reads `gate` (required), `commit_style` (required), `e2e` (optional) and `build_model` (optional) from `.agents/config.yml`. When the file is not valid YAML or a required key is missing, it stops, naming the key and the line to add, and it never guesses a gate from the repository. A guessed gate would earn validated markers for a check nobody chose, and `setup` does not exist yet to write the keys.
- All four presets of ADR 0003 (`arlo`, `arlo-features`, `conventional`, `plain`) ship as prose files in `skills/build/styles/`. `commit_style` may also name a path to a style file in the repository. If the config could name a preset that does not ship, that would be a broken config waiting to happen.
- The coding agent is an ordinary subagent that `build` starts, pointed at a sibling file `SLICE.md` in `build`'s folder, with only the plan path, slice id and start commit. This adds no new kind of plugin component (no `agents/` folder) and no extra skill in the `/` menu.
- The coding agent runs on the model `build_model` names, `sonnet` by default. Its instructions rely on nothing `sonnet`-specific, so it works on any model. Coding is the easier part once `grill` has made the decisions, possibly on a stronger model.
- `build` itself has no `model:` line and runs on the session's model. A skill cannot apply a model from config to itself, and its judgement calls go to the user as rounds anyway.
- When the coding agent meets a question no decision answers, it returns the question. `build` puts it to the user through `grilling`, adds the answer to the decision log, and resumes the same agent with SendMessage. A fresh agent would re-explore what the first already learned.
- A slice's challenge runs once. Its defect findings go back to the coding agent, which applies them as the commit style says (fixups, or commits of their own), with no step from the user. Its question findings are put to the user as a round when `build` stops. A fact settles a defect, so asking about one wastes the user a round.
- In `/build <feature>`, a slice's question findings do not stop the run. They are collected and put to the user, with the whole-branch challenge's questions, as one round at the single stop at the end, and ADR 0004's "stops once" stands. `grill` and `slice` are expected to have settled every decision, so `build` should raise no questions. A later slice built on a question that changes it is fixed by a `/slice` rework. Rejected: stopping the run at the first slice with a question.
- `/build S3 <comment>` turns a review comment on an unmerged `done` slice into fixups on S3's commits. `/slice` rework stays for squashing, reverting or rebuilding. ADR 0003 already makes a correction from review a fixup.
- Whenever fixups or a rework rewrite commits that others sit on, the gate reruns on every rewritten commit (for example, a rebase with `--exec`), not only on the tip. ADR 0002's attestation is per commit. The cost is accepted even for a slow gate such as Bazel.
- `build` never commits with `--no-verify`, even where a pre-commit hook runs the gate a second time. Skipping a hook the user installed is not `build`'s call.
- `/build S3` is allowed while an earlier slice is still `todo`, as long as every slice in S3's `Blocked by` is `done`. Otherwise it refuses and names the blocking slice. `Blocked by` is the dependency the plan records.
- Closing is the explicit command `/build close [plan]`, also written `/build [plan] close`, with the plan defaulting as in `slice`. Running it is the user's approval of the last slice, and it refuses while any slice is `todo` or `rework`. Plain `/build` only lists the slices and suggests the next one. An explicit command is clearer than a yes/no prompt, and closing early would delete a plan that open slices need. Rejected: closing on a yes after a plain `/build` once every slice is `done`.
- At close, `build` suggests which decisions to promote to ADRs, each with its reason, and the user picks. Whether a decision would surprise a later reader is a judgement, so it belongs to the user (ADR 0001).
- `build` opens a pull request at close whenever `origin` is on GitHub and `gh` is logged in, whatever `tracker` says. Without a pull request, it makes a local `--no-ff` merge into the default branch, with the decisions in the merge message, and never pushes the default branch. The tracker decides where slices live, not whether review happens in pull requests.
- `build` pushes the feature branch only at close, to open the pull request, and never while slices are being built. Fixups and reworks before close then need no force-push. The cost is no remote backup until close.
- Once `close` has deleted the plan and pushed, pull request comments are handled as ordinary commits outside `build`, and `/build S3 <comment>` works only before close. With the plan gone, nothing finds S3's commits, and the user approved before close.
- JobSensai stays out of the skills repository. Evals run on their own fixture repositories, and the first JobSensai feature built with `/build` after this merges is the end-to-end test. Its findings come back as issues or a `retro`. This keeps the skills independent of JobSensai and eval cost within budget, which a Bazel gate would not.
- A slice's row is set to `done` in its real last commit, once the challenge's corrections are in. When a correction stays as its own commit, the row change moves onto it. Otherwise the range rule loses such a commit to the next slice.
- ADR 0004 is amended, in the slice that builds out-of-order building, so that slices are built once every blocker is `done` and "the slice before it" means the one earlier in the branch's history. ADRs state what the skills do.
- The whole-branch challenge of `/build <feature>` is treated like a slice's challenge: its defects become fixups on the commits they correct, with the gate rerun on every rewritten commit, and its questions are put to the user at the stop. Its plan lens checks the diff against the whole plan (every slice and the decision log).
- A red gate from a wrong premise takes the same route as a coding agent's question: a `grilling` round in the session, the answer added to the decision log, then the agent resumes. When the answer changes a slice's behaviour, `build` stops and names `/slice` instead. ADR 0005 is amended to match, since one skill cannot call the user-invoked `grill`.
- Before building anything, `build` checks `.agents/config.yml` and stops, naming the problem, when `commit_style` names neither a preset nor an existing file, `extends:` goes two levels deep, `gate` or `e2e` is empty or not a string, `tracker` has another value, or `tracker: github` while `gh` is missing or not logged in. An unknown `build_model` cannot be checked in advance, so it fails when the first agent starts, and `build` stops with that error. A bad key found mid-feature would leave slices half-built.
- `build` stops, naming each problem and building nothing, when the plan has no `**Branch:**` line or no slices table, the table breaks `slice`'s rules, `Blocked by` names a slice that does not exist, a `rework` row has an empty note, the named slice is not in the table, or `tracker: github` while the table has no `Issue` column. In that last case it also names `/slice` to mirror the slices. Fixing the plan itself would change what the user approved.
- When the gate fails partway through rewriting history, `build` aborts the rebase, restores the branch exactly as it was, and stops, reporting the commit that went red and the kind of failure (ADR 0005). Rejected: trying ADR 0005's three fixes mid-rebase, which can leave the repository half-rewritten.
- ADR 0007 is amended, in the slice that builds close, so that at close `build` suggests promotions, each with its reason, and the user picks.
- One argument rule covers every form: `/build [plan] [S<n> [comment] | close]`, plus `/build close [plan]`. The first word is the plan when it is a path or names a folder under `docs/work/`. Otherwise `build` uses the only plan, or asks which one and stops. A plan alone builds every remaining slice. `close` is the command only as the first word or right after the plan, and everything after a slice id is the comment. Restricting `close` to one position was rejected, since the position rule already resolves the ambiguity.
- When the coding agent cannot go on without a decision, or a red gate shows a wrong premise, `build` still asks in the session, as above, rather than guessing. Its report also records that the planning missed the question, as a line for `retro`, so that `grill` and `slice` can be improved. Guessing breaks ADR 0001, and sending the user to `/grill` costs a whole session for one answer.
- A rework changes the table this way: a squash keeps the lowest-numbered row, merges the absorbed behaviour into it and removes the absorbed rows; a revert removes the row; a rebuild keeps it. The surviving row returns to `done` in the rework's last commit, a feature run's "every remaining slice" includes `rework` rows, and an issue `/slice` reopened for a rework closes again when the rework is done. This keeps the range rule working, and these are the shapes `slice`'s rework proposes.
- `/build S<n> <comment>` refuses a `todo` slice (naming `/build S<n>`), a `rework` slice (saying to drop the comment) and a merged slice (checked through `origin/HEAD`). A comment corrects something built, and treating it as build guidance would bypass the plan.
- `challenge` gains its plan lens in a slice of this feature, taking `<plan> <slice id> <range>` or `<plan> <range>`, since the per-slice and whole-branch challenges need it and ADR 0006 promises it.
- The gate rerun on every rewritten commit, with abort-and-restore on red, is built with the first slice that rewrites history, the per-slice challenge.
- Eval fixtures for `build` have a local bare `origin` with `origin/HEAD` set and start with the plan uncommitted, and the `gh` stub learns `pr create`. Each kind of red-gate failure, and the argument rule, gets its own case, so a test cannot pass while one route is missing.
